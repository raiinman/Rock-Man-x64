# Specification: documentation-tracker

## Assumptions and objective

[Shared specification](SPEC.md) applies. This is a read-only documentation system, not a game controller or automatic evidence assessor. Preserve reviewed evidence, honest numeric projections and verifiable publication.

## Provider-owned interface

[TRACKER.md](docs/status/TRACKER.md) and [status ownership](docs/status/AGENTS.md) define canonical schema-3 evidence, schema-2 receipts, stable IDs, versioned criteria and append-only observations. [Tool ownership](docs/status/tools/AGENTS.md) defines the five generated outputs. [Web ownership](docs/web/AGENTS.md) defines immutable artifact projection; [workflow ownership](.github/workflows/AGENTS.md) defines existing bounded automation and Pages permissions.

Inputs are reviewed public-safe evidence about the other modules. Outputs are deterministic Markdown/SVG/JSON and static HTML/CSS/ES modules. Reporting dependencies do not grant the tracker native APIs or acceptance authority. Public `analysis-tooling` coordination remains only the existing narrow handoff exception; private tooling state is excluded.

## Commands, style and tests

Use the complete commands and actual public validation example in [SPEC.md](SPEC.md#verified-commands-and-flags). Python standard-library `unittest`, Node built-in mock-DOM/model tests and static artifact/workflow checks are the existing frameworks. No installs, network access or private fixtures are required. Source code and workflow behavior are unchanged by adoption.

## Separate build/spec-plan view

The separate build/spec-plan route projects explicit reviewed states from canonical `build_plan` metadata. Task IDs and dependencies must match their cited definitions; build checks resolve cited evidence updates. No task checkbox, dependency, test count or historical ratio supplies a state or overall game percentage. A bounded working private IDE interaction is distinct from full IDE, native boot and playable-game acceptance. The existing checksum receipt, five generated paths and eight-file Pages artifact remain in force.

## Success and failure semantics

- Native acceptance flags, criteria, versions, stage evidence and historical observations cannot be changed merely to record this adoption.
- Candidate validation passes with preserved research/license/history and exact internal links. The eventual documentation review appends one honest zero-acceptance-delta observation through the existing contract.
- Missing citations, inconsistent receipts, unsafe content or stale generated outputs fail closed. Never manually edit generated files or widen the five-output allowlist.
- Publication is not complete until the authorized exact remote revision and actual workflow/deployment outcome are verified. A local draft is not a live tracker update.

## Current adoption boundary

The reviewed map/spec/DOX/adoption-task documentation and owner-requested worker policy have one canonical documentation review and zero-acceptance-delta observation. Publication remains a separate exact-diff and delivery-verification step in [the adoption plan](tasks/plan.md); local review or passing checks do not assert a completed remote update.
