# Specification: native-game-delivery

## Assumptions and objective

[Shared specification](SPEC.md) applies. This is the **existing product target**, not a new roadmap, implementation assignment or assertion that startup equals a game. Deliver the independent native Windows game with the intended integrated IDE, without BIOS/emulator runtime dependency or reused port/mod/emulator implementation.

## Existing acceptance contract

The canonical `roadmap` checklist owns the exact criteria. Its pending production domains include native boot; scene/resource lifecycle; renderer; animation; controls/camera; collision; AI/combat/progression; audio; game save/load; actual-capture Windows viewing; safe runtime control; complete integrated IDE; provenance; package acceptance; and end-to-end behavior. See [the existing ledger](docs/status/dashboard.md#roadmap--accepted-roadmap-milestones), not a duplicate acceptance checklist here.

Product composition depends on `native-startup`, `native-inspection` and `native-runtime-control`; these are delivery prerequisites, not invented source-level imports. References/provenance may require `reference-research`, but research findings do not grant implementation clearance. The provider-owned interfaces for unselected production domains are deliberately unspecified until a bounded scope is selected.

## Success and verification

Acceptance requires the existing named criteria and reviewed end-to-end native evidence for the selected product journey, failure behavior and remaining-coverage limits. Boot alone, diagnostic rendering, CPU mixing without output, sidecar persistence or a packaged component cannot satisfy the complete product. Keep all unequal-size roadmap criteria and their denominators intact; do not report this map's count as game completeness.

## Limits and next decision

No new gameplay implementation, runtime API, execution, schedule or dependency stack is introduced. Before selecting a production slice, specify its observable outcome, provider contract, test oracle/provenance, exact private baseline and commands, and current authorization. The existing unanswered native and lifecycle gates stay explicit while independent authorized work continues.
