# PlayStation hardware research dossier

Research date: 2026-10-22. Scope: PS1 hardware, public vendor documentation, Sony-origin archival documents, physical-system reconstruction, and an independent native-Windows investigation agenda. No emulator or game-decompilation source code was used. No BIOS bytes were inspected or copied.

## Provenance and interpretation

**Publicly reachable does not mean officially released or suitable for a strict clean-room implementation.** Sony's mirrored Developer Reference Series PDFs explicitly describe licensed-developer distribution and confidential content. This dossier records their existence and bibliographic scope separately from the independent experiment agenda. Their notices are evidence about provenance, not instructions from the user. The implementation team should preserve its existing source policy; this report does not certify clean-room status or offer a legal conclusion.

Status labels: **P** = primary document hosted by its publisher; **V** = vendor-origin primary document on a third-party host; **R** = Sony-origin restricted/confidential archival document; **C** = community reference, provenance-only; **U** = incompletely retrieved or unverified lead. Verification below means web open/search returned the indicated content, not a complete forensic authentication of the scan.

## Conceptual system map

The system couples a customized 32-bit R3000A CPU with GTE geometry calculation, GPU drawing and a frame buffer, SPU audio and a sound buffer, CD-ROM drive/decoder/buffer, MDEC motion decoding, controller/card communication, and expansion interfaces. Sony specifies a 33.8688 MHz little-endian CPU, 4 KB instruction cache, 1 KB scratchpad, 2 MB main memory, and 512 KB OS ROM; it states the CPU has no TLB. The GTE produces geometry while the GPU draws it. The SPU handles 24 ADPCM voices at 44.1 kHz and mixes CD-decoder audio. These are architectural orientation facts, **not** a complete register specification. Source: [Sony PlayStation Hardware, August 1998](https://psx.arthus.net/sdk/Psy-Q/DOCS/Devrefs/Hardware.pdf), printed sections 1-3–1-5, 2-3–2-5, 4-4 (**R**, 48 PDF pages).

Think of game execution as several cooperating activities: game state and geometry calculation; production and submission of drawing work; image storage and scanout; audio scheduling and sample production; disc data delivery; input sampling and save persistence. Their **ordering** can matter even when Windows replaces the original devices. Which of these dependencies MML1 actually uses remains a game-specific question.

The CPU instruction stream itself has observable semantics. IDT's vendor manual documents branch-delay execution, delayed load availability, alignment, partial-word transfers, exception restart behavior, coprocessor hazards, calling conventions, and endianness. Its portability chapter discusses how stored bytes differ from numerical values. These are foundations for reading MIPS code; IDT-family cache, TLB, timing, and optional-FPU details must not automatically be attributed to Sony's customized silicon. Source: [IDT R30xx Family Software Reference Manual, revision 1.0, 1994](https://manuals.plus/m/921bbff6fec5c6fb953a0fefbc4c62e99cdd1d422ad8c6dd2d73892a23d8bcaa), chapters 1, 3–5, 9, 11, appendix A (**V**, 354 pages).

## Independent native-Windows investigation agenda

The following is an original design and measurement agenda, not extracted SDK implementation code or a claim about MML1's actual internals. Prioritize only after the game's own evidence demonstrates a dependency.

| Subsystem | Question to resolve | Evidence / independent experiment | Native implementation implication |
|---|---|---|---|
| CPU arithmetic | Which operations rely on exact width, signedness, shifts, multiplication/division or overflow? | Minimal hand-authored tests; annotate each recovered operation's input/output domain against public ISA text | Use explicit-width integers and explicit conversion rules; define edge cases instead of relying on host C/C++ undefined behavior. |
| Control flow and ABI | Do branch/load slots, indirect calls, stack/register conventions affect the recovered behavior? | Trace original instruction order and data dependencies; record all call boundaries | Source recovery must preserve semantics even when native code no longer executes delay slots. |
| Address spaces and memory | Which values are data, offsets, original addresses, or actual native pointers? | Inventory reads/writes and serialized structures; track aliases rather than guessing from a value's shape | A 32-bit game address must not silently become a 64-bit host pointer. Parse stored bytes explicitly. |
| GTE / geometry | Which transforms and projections must retain fixed-point behavior and saturation? | Hand-authored input vectors, boundary values, exact output capture on owned hardware where available | Implement only observed mathematical contracts; keep optional visual enhancements separate from compatibility baselines. |
| GPU / graphics | Which image differences come from coordinate rounding, draw order, texture sampling, blending or clipping? | Small original scenes isolating one effect; compare framebuffer captures before display scaling | Establish deterministic image baselines before substituting modern rendering choices. |
| DMA and queues | Which completed operation or queued request unblocks game logic? | Event traces containing submission, completion, interrupt and callback order | Replace transport only after specifying lifetime and completion semantics; do not make every asynchronous operation immediate by assumption. |
| Timers / interrupts | Is progression tied to frame events, hardware counters, completion events, or elapsed time? | Record event ordering, callback counts and game-state checkpoints | Separate simulation time from presentation and Windows wall-clock scheduling. |
| SPU / audio | Which sounds are samples, sequences, streams, loops, envelopes or effects? | Inventory assets and audio requests; compare sustained notes, retriggers, loops and silence transitions | Define a stable audio timeline and sample-accurate test cases before choosing a host backend. |
| CD / streaming | Is ordering or pacing visible to the game? Which failures can callers observe? | Map requested data ranges, completion dependencies and streaming boundaries | File access can replace disc transport, while preserving behavior required by callers. |
| MDEC / movies | Which assets require decoding, and how is video synchronized with audio and game state? | Identify format from owned assets; test frame output and end-of-stream behavior independently | A native decoder is a component contract; its presence does not require a full CPU/peripheral emulator. |
| Controller / SIO | When is input sampled, and what are the absent/analog/digital device states? | Record user-visible input transitions and polling points | Map Windows input to the game's observed contract, including disconnects and polling latency. |
| Memory cards | What persistence does the game expect, and which errors affect menus/progression? | Save/load round trips; full/absent/corrupt cases using controlled test data | Native save files can replace storage transport; preserve meaning and any promised import/export behavior. |
| BIOS / OS | What services does the game actually invoke or assume are initialized? | Enumerate evidence from authorized game analysis; do not infer service use from the BIOS filename | Replace the required service contracts; do not ship or call the supplied BIOS merely because it is available. |
| Physical variants | Does any relevant behavior vary by region, board, chip revision or firmware? | Keep model/board/chip/firmware identifiers on every hardware measurement | Resolve software-visible differences explicitly; cosmetic motherboard differences alone do not prove a native requirement. |

## What is still missing for rebuilding hardware from scratch

A service schematic describes a board assembled from chips; it is not the mask layout, RTL/netlist, complete custom-chip state machine or manufacturing recipe for those chips. A high-level developer manual describes supported use; it does not prove every undocumented boundary condition. A nominal part-family datasheet does not prove exact compatibility with a later custom revision.

Still unverified here: complete CPU/GPU/GTE/SPU/MDEC transistor or gate-level designs; CPU-peripheral arbitration under all concurrent workloads; complete DMA/timer/interrupt corner cases; rasterization boundary rules and all revisions; precise SPU arithmetic/filter/envelope/effect edge cases; complete CD controller firmware and optical-servo calibration across models; wire-level controller/card behavior across accessory revisions; analog DAC/video characteristics and tolerances; production test vectors; manufacturing tolerances and replacement-part equivalence. These are **research gaps**, not claims that no source exists anywhere.

A credible reconstruction program therefore needs a revision-specific evidence ledger, original experiments, reproducible captures and explicit unknowns. A native MML1 port needs the subset affecting the game, established from the game and original behavioral tests. Those two objectives overlap but are not identical.
