# Spec adoption tasks

## Purpose

Track the bounded initial spec-driven-development adoption without replacing ongoing native/research work or the canonical acceptance tracker.

## Ownership

`plan.md` owns the adoption sequence and checkpoints. `todo.md` records only that plan's execution state. Root capability/spec files own the adoption contract; existing domain owners retain implementation and evidence acceptance.

## Local Contracts

- Preserve incomplete plans and task history. Extend the same work in place; ask for a destination before introducing different work over an unfinished plan.
- Do not duplicate canonical roadmap acceptance or private worker checklists, mass-close tasks or turn a task checkmark into capability acceptance.
- Keep private details outside this public tree. Publication and tracker-review tasks remain pending until their actual authorized result exists.

## Work Guidance

Use dependency-ordered vertical checkpoints with observable completion evidence. Unresolved consequential scope/API/provenance gaps block dependent work, not independent authorized tasks. Existing settled authority carries forward without automatic reapproval.

## Verification

Check links, checkbox truthfulness, exact changed paths, whitespace and the public documentation commands in `../SPEC.md`. No native execution is required for this adoption.
