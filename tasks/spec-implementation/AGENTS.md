# Specifications-derived implementation planning

## Purpose

Maintain the owner-requested dependency-aware breakdown of the shared specification and seven capability specifications.

## Ownership

`plan.md` owns decisions, dependency order, readiness gates and checkpoints. `todo.md` owns planning task descriptions and execution state; it is not a second acceptance tracker. Existing native/research owners retain their actual implementation queues and patch ownership.

## Local Contracts

- Preserve the parent adoption plan and execution list verbatim. Extend this same-scope plan in place; obtain a destination decision for different unfinished work.
- Canonical criteria, states and observations remain in `../../docs/status/dashboard-data.json`. Task completion never changes acceptance automatically.
- This is planning only. Conditional implementation descriptions grant no execution, source access, publication, S2 or initializer authority. Switchboard remains paused; Atlas navigation and presentation redesign are separate work.
- Keep source commands, paths, identities and artifacts private. Unknown private targets are named evidence dependencies, never guessed paths or commands.

## Work Guidance

Use stable task IDs, provider-first dependencies, focused vertical slices and checkpoints after two or three tasks. Resolve a consequential contract or evidence gap before dependent implementation. Record actual ownership and availability before assignment; do not duplicate existing work or unanswered handoffs.

## Verification

Validate local links, criterion IDs, dependency order, task acceptance/verification, privacy and whitespace. Run the public documentation checks in `../../SPEC.md`; native/game/BIOS/emulator tests are outside this planning task. Exact-diff parent review precedes any push; tracker integration remains with the coordinator.
